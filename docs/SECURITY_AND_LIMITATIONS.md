# 보안 및 실서비스 도입 전에 반드시 확인할 사항 (v0.7)

**중요:** 서버에 데이터가 실제 저장되고 계정별로 접근이 차단되는 파일럿 구현입니다. 개인정보·피부 상태·사진·상담 동의 등은 보안/법률 및 운영 프로세스의 검증 없이 실고객 데이터에 사용하지 마세요.

## 현재 구현한 조치

1. Supabase Auth 이메일 인증과 JWT 사용자 식별.
2. 매장별 `shop_id` RLS 조회 정책. 익명(anon) 데이터 접근 불가.
3. 쓰기는 `ongeol_save_state` PostgreSQL RPC 트랜잭션에서 매장 소속·상태 형식·버전 검사.
4. 다른 기기에서 먼저 저장하면 `stale_revision` 충돌로 덮어쓰기를 차단. 사용자는 새로고침해야 함.
5. 피부사진은 private Storage 버킷, 매장 경로 정책, 제한 시간 서명 URL, 3MB/이미지.
6. Supabase DB 관리자/secret 키 및 LLM 비밀키를 공개 웹앱에 포함하지 않음.
7. 고객 없이 새 매장을 만들며 데모 샘플이 자동 주입되지 않도록 변경.
8. 광고 수신, 녹음, 사진 동의를 별도 값으로 보관; 상담 AI가 고객 프로필을 자동으로 무단 수정하지 않도록 기존 승인 흐름 유지.

## 제한 및 상용화 전 필수 개선

| 중요도 | 내용 |
|---|---|
| 최우선 | **현재 업무 데이터는 매장별 JSON document 하나**에 저장됩니다. PostgreSQL 개별 예약/결제/회원권 행이 아니므로 서버 측 예약 충돌 검사, 회원권/재고 동시 차감의 원자성, 정규화 FK가 아직 없습니다. 여러 직원이 동시에 운영하려면 예약·회원권·결제 테이블을 정규화하고 전용 트랜잭션을 구현해야 합니다. |
| 최우선 | **직원 역할별 필드 권한(RBAC)이 미완성**입니다. 매장 소속 누구든 고객/상담/매출 JSON을 읽고 수정할 수 있습니다. 원장 1인 파일럿부터 시험하고 직원 초대는 신뢰 관계/권한정책 정비 후에 사용하세요. |
| 최우선 | 고객 피부 상태, 알레르기 등 민감한 정보가 들어갈 수 있습니다. 개인정보 처리방침, 동의 근거/문서 버전, 보유기간, 삭제/열람 권리, 개인정보 처리 위탁 및 국외 이전/저장 위치 등은 관계 법령과 업체 계약을 검토해야 합니다. |
| 최우선 | **삭제/정정·동의 철회 워크플로우**가 운영 규정 수준으로 완성되지 않았습니다. 비공개 사진 파일까지 연쇄 삭제하는 업무 기능 추가 필요. |
| 필수 | Supabase Free는 자동 백업이 없고 휴면 정지가 있습니다. 백업/복원 검증과 장애 대응 계획이 필요합니다. JSON 내보내기에는 개인정보가 포함될 수 있으므로 안전하게 암호화·보관하세요. |
| 필수 | 비밀번호 분실/재설정, 계정 탈퇴, 세션 강제 종료, 직원 퇴사 시 권한 회수, 다중 계정 접근 로그 정비. |
| 필수 | 모바일 실제 기기·다중 사용자 E2E 테스트, API 요청 속도 제한, 보안 취약점 검사 및 모니터링. |
| 참고 | 사진 서명 URL은 1시간짜리 임시 접근권한이며, URL이 공유되면 만료 전까지 접근될 수 있습니다. 저장하지 말고 사용자 기기에서 다뤄야 합니다. |
| 참고 | 오프라인 편집은 없습니다. 네트워크 오류가 나면 저장 실패 메시지가 나며 사용자가 서버 상태와 비교해야 합니다. |
| 참고 | 실카드 결제, 실제 예약톡·알림톡, 외부 검색 지표, AI/STT는 미연결. 화면에서 시뮬레이션/수동 입력으로 분리됩니다. |
| 참고 | PWA는 웹앱이며 Android APK, iOS 앱스토어 파일이 아닙니다. |

## API 키 분리

- 브라우저 `config.js`: Supabase URL, **publishable key**만.
- 나중에 Edge Functions의 secrets: LLM/STT API Key, 알림톡/SMS 제공업체 인증정보, 검색 API Key.
- 절대 브라우저에 두지 않기: DB password, Supabase secret/service_role key, JWT signing secret, 결제 비밀키.
